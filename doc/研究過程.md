# 研究過程

## Project 介紹

本專案目標是在 **Llama 3.1 8B-Instruct** 上重現並改良 [FINCH](https://arxiv.org/abs/2306.14048) 的 KV cache 壓縮方法，並在 **LongBench v1/v2** 上與 FullKV（無壓縮）基準做對比。

### 什麼是 FINCH？

FINCH 是一種 attention-score-based token dropping 方法：
- 把 context 切成固定大小的 chunk（split_size），chunk-by-chunk 送入模型
- 每個 chunk 結束後，根據 question/context 的 attention score 保留 top-k 個 KV cache entries
- 重複迭代直到整個 context 處理完，最終 KV cache 壓縮到 `target_token` 以內

### 比較方法

| 方法 | 壓縮方式 |
|---|---|
| FINCH（本專案） | attention-score token dropping，固定 target_token |
| FullKV | 無壓縮，全部 token 保留 |
| LiveKVQuantP （作者提出的） | Chunk-wise approach，直接在 KV cache 上做量化，不丟 token |
| KVQuant | KV value 量化（4-bit 等） |

### 比較基準

**固定記憶體（壓縮率），比較 F1 score + latency + memory_peak**

- `target_token` 設為 `rate × avg_len`，使各方法平均記憶體用量等價，每項任務的 target_token 不一樣，可以參考 [任務細節.md] 
- **target_token 一旦確定就不能改動**，否則不同實驗之間的比較失去意義

## 核心問題：Llama 3.1 為什麼比 Llama 2 結果差？

FINCH 原論文使用 Llama 2，在 narrativeqa 上跑出 19.1（512 target tokens，σ=93x 壓縮率）。
我們在 Llama 3.1 上，用更寬鬆的設定卻只能跑出 12-15，差距顯著。

**這不是模型能力退步，而是 FINCH 的 attention top-k 機制在 Llama 3.1 上更容易失真。** 根因有三層：

### 根因 1：GQA 使 attention sum 的信噪比下降

| | Llama 2-7B | Llama 3.1-8B |
|---|---|---|
| Attention 架構 | MHA | GQA |
| KV heads | **32**（每個獨立） | **8**（每個被 4 個 Q head 共享） |
| Query heads | 32 | 32 |

FINCH 的核心操作：`layer_attention.sum(dim=1)`（把所有 head 的 attention 加總做排序）

- **Llama 2**：32 個獨立 KV head → 32 組獨立 attention pattern 投票 → 加總後信號穩定
- **Llama 3.1**：實際獨立投票只有 8 組，信噪比降約 **4×**，排序穩定性更差

### 根因 2：RoPE theta 大幅提升，attention 分布更平坦（最根本原因）

| | Llama 2 | Llama 3.1 |
|---|---|---|
| rope_theta | 10,000 | **500,000** |
| 訓練 context 長度 | 4k | **128k** |

- **Llama 2**：attention 有明顯「局部峰值」→ top-k 容易選到真正相關的 token
- **Llama 3.1**：attention 更**平坦** → 第 100 名和第 500 名的分數差距很小 → top-k 容易選到無關 token

### 根因 3：迭代壓縮的複合誤差，長文件任務最嚴重

每輪 re-selection 都有小誤差，chunk 越多誤差越大：

| Task | Chunks 數 | re-selection 輪數 | (0.98)^N |
|---|---|---|---|
| qasper | 10 | 9 | 0.83 |
| multifieldqa | 14 | 13 | 0.77 |
| **narrativeqa** | **59** | **58** | **0.31** |

**數據佐證**（narrativeqa 按 context 長度分 bin）：

| Context 長度 | 樣本數 | FINCH F1 | FullKV F1 | 保留率 |
|---|---|---|---|---|
| 5k-10k（< target，未壓縮） | 19 | 26.76 | 26.76 | **100.0%** |
| 10k-20k（20-40 chunks） | 56 | 21.24 | 23.93 | 88.7% |
| 20k-30k（40-60 chunks） | 10 | **0.00** | 10.83 | **0.0%** |
| 30k-50k（60-80+ chunks） | 88 | **8.01** | 29.12 | **27.5%** |

三層根因疊加，完美解釋了為什麼 narrativeqa（長文件）掉最多，qasper/multifieldqa（短文件）相對好。

**一句話總結**：Llama 3.1 在 FINCH 下表現較差，主要來自「attention 更平坦 + GQA 投票信號較弱 + 長文件多輪壓縮誤差累積」三者疊加。

## 實驗過程與結論

### 背景設定

- `context_max_length` 全部設為 **128000**（讓 FINCH 看到完整文件，不在壓縮前截斷）
- `target_token` 為壓縮的唯一控制變數，決定保留多少 KV cache

```
原始文件 (任意長度)
  → 截斷到 context_max_length   ← 直接丟棄，FINCH 看不到
    → FINCH 壓縮到 target_token
```

---

### 假說 1：split_size 太小 → 過多迭代 → 加大可改善

**實驗**（narrativeqa，200 樣本，固定 target_token=9137）：

| 實驗 | split_size | F1 | 結論 |
|------|-----------|-----|------|
| Baseline | 512 | 12.62 | — |
| A | 2048 | 12.81 | 幾乎無改善 |
| B | 4096 | 9.15 | 反而更差（OOM 風險，attention 品質更差） |

**結論：split_size 不是瓶頸。** 加大 chunk 雖減少迭代次數，但每個 chunk 的 attention 信號更難聚焦，兩者相抵消。

---

### 假說 2：固定 target_token 對長文件過度壓縮 → per-sample adaptive 可改善

**實驗**（compression_rate=0.3063，per-sample adaptive target）：

| 實驗 | split_size | F1 | 結論 |
|------|-----------|-----|------|
| C | 512 | 8.25 | 比固定差 |
| D | 2048 | 9.71 | 仍比固定差 |
| E | 4096 | 5.22 | 最差（27 OOM） |

**結論：per-sample adaptive target 反而更差。** 長文件原本靠多保留 token 來彌補 attention 不準，adaptive 強制削減反而傷害更大。

---

### 假說 3：GQA 信噪比低 → per-head vote 可改善 ✓

**實驗設計**：把 32 Q heads reshape 成 8 KV groups，每個 group 獨立 top-k 後投票，用 vote count 取代 uniform sum。

| 實驗 | 設定 | F1 | vs FINCH orig |
|------|------|-----|--------------|
| per_head_vote | vote_r=k（最寬鬆） | **13.70** | **+1.08** ✓ |
| per_head_vote | vote_r=k/2（嚴格） | 11.61 | -1.01（更差） |

**結論：`per_head_vote=True, vote_r=k` 是最佳設定。** vote_r 縮小反而更差，說明 Llama 3.1 attention 太分散，嚴格的 majority voting 會誤丟重要 token。

**三 task 比較（FINCH+per_head_vote 改版前）**：

| Task | FullKV | FINCH orig | FINCH+per_head | Gap 縮小 |
|------|--------|-----------|---------------|---------|
| narrativeqa | 26.53 | 12.62 | **13.70** | 1.08（7.8%） |
| qasper | 46.94 | 35.17 | 34.77 | — |
| multifieldqa_en | 48.15 | 35.72 | **39.87** | 4.15（33.4%） |

multifieldqa 改善顯著（chunk 少），narrativeqa 改善有限（58 輪迭代複合誤差為方法固有限制）。

---

### Prompt Format 改版 ✓

**問題**：舊版 legacy mode 格式固定，無法靈活控制 context/question 的排版，且有 `question_prompt` bug（設定時會把實際 input sequence 一起替換掉）。

舊版格式：
```
<|system|>prompt<|eot_id|><|user|>context: {context}\nquestion: {input}<|eot_id|><|assistant|>
```

**改動**：新增 **template mode**，只要 yaml 的 `prompt` 欄位包含 `{context}` 就自動啟用。

```yaml
# 範例 yaml 設定
prompt: "Answer the question.\n\n{context}\n\nQuestion: {input}\nAnswer:"
```

template 字串被拆成三段（`before_context` / `ctx_input_sep` / `after_input`），模型看到的序列：
```
<bos><user> before_context + context + ctx_input_sep + input + after_input <eot><assistant>
```

同時修正 `question_prompt` bug：現在只影響 FINCH compression condition，不影響實際送入模型的 input sequence。

**結果**：換用新 prompt format 後整體結果有所改善。

### Completion Mode 修正 ✓

**問題根因**：`trec`、`samsum`、`triviaqa`、`lcc`、`repobench-p` 是 **completion-style** 任務——prompt 結尾就是答案標籤（`Type:`、`Summary:`、`Answer:`、`Next line of code:`），模型應該直接補全。但原本 `generate_input()` 一律加上 `<|eot_id|><|start_header_id|>assistant<|end_header_id|>\n\n`，導致：

- trec / samsum：模型被 chat template 引導，輸出完整解釋句而非簡短類別/摘要，且大量幻覺出 few-shot context 裡其他範例的內容
- triviaqa：`input` 欄位包含完整 passage（長達 3266 tokens），套上 chat template 後輸出完全失控（如 `22/23/24/25/...`）

**注意**：別處用LLaMA-3.1-8B-Instruct 直接做 inference 時（使用FastKV的程式碼跑的fullKV） ，能夠取得91.73的分數。但是這裡triviaqa 的 FullKV F1 在 logs 裡實際上也只有 17.06，也就是 Prompt 有問題(或其他原因導致)。

**修改**：新增 `completion_mode` 旗標，由 yaml 設定，讓 `generate_input()` / `generate_context()` 跳過 chat template headers。

| 檔案 | 修改內容 |
|------|---------|
| `src/custom_datasets/llama31_dataset_custom.py` | 新增 `completion_mode` 旗標；`generate_input()` 在 completion_mode 下不加 `<|eot_id|><|assistant|>` |
| `conf/custom_datasets/trec_custom.yaml` | 加 `completion_mode: True` |
| `conf/custom_datasets/sam_sum_custom.yaml` | 加 `completion_mode: True` |
| `conf/custom_datasets/trivia_qa_custom.yaml` | 加 `completion_mode: True`（主要 bug 修正） |
| `conf/custom_datasets/lcc_custom.yaml` | 加 `completion_mode: True` |
| `conf/custom_datasets/repobench_custom.yaml` | 加 `completion_mode: True` |

**預期效果**：triviaqa FullKV/FINCH 大幅提升；trec/samsum 格式輸出正常化（few-shot compression 本身的問題仍存在，但至少不再幻覺）。

### triviaqa FullKV 深度除錯（2026-03-16）✓

**問題**：completion_mode 修正後，triviaqa FullKV 仍只有 34.11（FastKV 參考值 91.73），差距過大。

**根本原因診斷（三層）**：

**層 1：`generate_context()` 加了錯誤的 chat headers**
原本 completion_mode 下 `generate_context()` 仍會輸出 `<|begin_of_text|><|start_header_id|>user<|end_header_id|>\n\n`，使模型認為自己在 user turn 中間——沒有 `<|eot_id|><|assistant|>` 結尾，模型不知道要轉為回答角色，繼續生成 passage 內容。FastKV 完全不加任何 chat headers，純 `<|begin_of_text|>` + 文字。

**層 2：`max_length: 512` 截斷了 input（最根本原因）**
`tokenize()` 呼叫 `tokenizer(inputs, targets, truncation='longest_first', max_length=512+32)`。triviaqa 的 `input` 欄位 = `Passage:\n...\nQuestion:\nXXX\nAnswer:\n`，token 長度最長達 **1870 tokens**，127/200 樣本超過 512。截斷後 `Answer:\n` 消失，`input_ids_for_generation` 以 passage 中間的文字結尾，模型完全不知道要回答問題，繼續抄 passage。

**層 3：生成後沒有截取第一行**
completion_mode 下模型有時給完答案後繼續生成 passage 後續內容，需要 `split('\n')[0]` 取第一行。

**修改**：

| 檔案 | 修改內容 |
|------|---------|
| `conf/custom_datasets/trivia_qa_custom.yaml` | `max_length: 512 → 2048`（主修正）；`completion_mode: True`；新增 `extract_question_from_input: True` |
| `src/custom_datasets/llama31_dataset_custom.py` | `generate_context()` completion_mode 路徑改為純 `<|begin_of_text|>` + 文字（無 user/system headers）；新增 `extract_question_from_input` 旗標讓 FINCH condition 只用 `Question:` 後的文字 |
| `src/predictors/language_modeling_predictor.py` | completion_mode 下對輸出做 `split('\n')[0]` 取第一行 |

**結果**（全 200 samples，FullKV）：

| 版本 | avg F1 |
|------|--------|
| 修正前（max_length=512, completion_mode 有 chat headers） | 34.11 |
| **修正後（max_length=2048, 純 raw completion）** | **79.10** |
| FastKV 參考值（LLaMA-3.1-8B-Instruct） | 91.73 |

剩餘 ~12 分差距的可能原因：`repetition_penalty: 1.2`（FastKV 無此設定）、BPE tokenization 邊界微小差異。

方案 1：移除 repetition_penalty（成本低，效果可期）
```python
# qa_lm_predictor.yaml 或 evaluate_triviaqa.yaml override
```
repetition_penalty: 1.0
方案 2：max_answer_length 調整

目前 32 tokens，FastKV 也是 32。應該沒差。

方案 3：檢查 split('\n')[0] 是否誤截斷某些正確答案

有些答案可能本身含 \n（機率低），但可能有些正確答案被截到空字串（如 id=4 輸出 . 就是因為 passage 中間截斷）。可以改成 split('\n')[0].strip() 取第一個非空行：

```python
lines = [l.strip() for l in clean_text.split('\n') if l.strip()]
clean_text = lines[0] if lines else clean_text
```
方案 4：換成 min_length 確保模型輸出至少一個 token 才能停

FastKV 設了 min_length=context_length+1，我們沒有。這讓模型不能在沒生成任何 token 的情況下就停（EOS）。

## 分析：lcc / repobench-p 低分根因（2026-03-17）

**假說**：condition="question" 時 query "Next line of code:" 語義貧乏，改 condition="all" 應改善。

**實驗結果**（`logs/20260317_131309_lcc.json`）：

| condition | lcc F1 |
|-----------|--------|
| "question"（v3） | 28.56 |
| "all"（本次） | 27.88 |

**無改善。** 問題不在 condition。

**根本原因**：FINCH 純依賴 attention score 全局排名選 token，對 token 的位置無任何偏好。程式碼補全任務的關鍵是 **cursor 前最後幾十行**（locality），而非語義相關 token。FINCH 壓縮後這些 local context 被 evict，模型失去局部脈絡，輸出 ` ``` `、`# comment` 等無意義內容。

觀察到的 bad outputs：

| id | output | ground_truth |
|----|--------|--------------|
| 0 | ` ``` ` | `Participant p = (Participant)m_Participants[i];` |
| 5 | ` ```python ` | `longest = max(self.answers)` |

**結論**：Attention-based token dropping（FINCH、H2O 等）對 code completion 有系統性弱點——缺乏 recency bias。改善需要在 token selection 中強制保留 tail tokens（pin_tail），已超出 FINCH 原始設計範疇。

## 分析：passage_retrieval_en 低分根因（2026-03-17）

**現象**：FullKV=100，FINCH v3=17（`logs/v3_result/20260316_193208_passage_retrieval_en.json`）。gap 極大。

**任務結構**：context 含 30 段 Wikipedia 段落（各 ~400 tokens，共 ~12k tokens），question = 某段落的摘要，task = 輸出對應的 "Paragraph X"。本質是 "needle in a haystack" 精確查找。

**metric**（`retrieval_score`）：抽出 prediction 中的數字，與 ground_truth 中的段落編號比對，完全一致才得分。等同 accuracy（0 or 100）。

**壓縮設定**：target_token=4191，保留約 35% tokens，相當於保留 ~10/30 段落。

**根本原因**：

1. **Wikipedia 文本風格均一，attention 無法區分目標段落**：30 段都是百科全書風格，詞彙分布相似。query（摘要）對各段落的 attention score 幾乎無差異，FINCH 的 top-k 選擇退化為近似隨機選擇。

2. **"Paragraph N:" 結構標記主導 attention**：prompt 要求輸出 "Paragraph X" 格式，模型對每段的結構標記都有高 attention，拉平了所有段落的分數，target 段落的實際內容得不到額外加分。

3. **此任務要求完整保留 target 段落**：QA 等任務中，保留任何高相關 token 都能幫助回答。但 passage_retrieval 需要模型讀到 target 段落的完整內容才能識別它——partial retention 是致命的。

**為什麼 17% 比隨機（~35%）還低**：即使 target 段落 token 被部分保留，其他 29 段的殘留 token 片段仍會干擾模型，使它指向錯誤的 Paragraph。

**結論**：Attention-based token dropping 對 exact retrieval 任務有結構性缺陷。所有段落 attention 均一 → 壓縮近似隨機 → target 大量丟失 → 準確率崩潰。此類方法在 "needle in a haystack" 任務上的低分是**預期內的系統性失敗**，無法靠調參改善。
