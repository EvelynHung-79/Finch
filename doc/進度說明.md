# 進度說明

## Condition 選擇策略（重要）

| Condition | 適合任務 | 原因 |
|---|---|---|
| `question` | 單文件 QA、多跳 QA | Question tokens 能看到全部 context（causal），attention 直接反映相關性 |
| `context` | 摘要（summarization） | 沒有明確問題，用 context 自身 attention 保留重要句子 |
| `all` | 合成任務（passage retrieval/count）、code | 語意本身就分散，需要全域 attention |

**注意：`condition="all"` 不適合多跳 QA。** 實測 2wikimqa F1 從 12.99（question）降到 5.7（all）。
原因：context tokens 在 causal mask 下看不到後面的 question，其 attention score 跟 question 無關，
壓縮判斷被語言模型局部 pattern 主導，傾向保留靠前 token 而非 question 相關 token。

---

## context_max_length 與 target_token 的角色釐清（重要）

`context_max_length` 是 **dataset preprocessing 的硬截斷**，發生在 FINCH compression 之前：
`context_max_length` 全部設為 **128000**，讓 FINCH 看到完整文件，不在壓縮前截斷。

```
原始文件 (任意長度)
  → 截斷到 context_max_length   ← 直接丟棄，FINCH 看不到
    → FINCH 壓縮到 target_token
```

**不能把 context_max_length 當作 compression rate 的分母。**
`target_token` 才是控制壓縮量的變數。

---

## 比較實驗設計（重要）

### 三個比較方法

| 方法 | 壓縮方式 |
|---|---|
| 我的方法 | 混合精度，per-sample adaptive，rate 由方法本身決定 |
| FINCH | attention-score token dropping，固定 target_token |
| KVQuant | KV value 量化（4-bit 等），rate 由 bit-width 決定 |

### 比較基準

**固定記憶體（壓縮率），比較 F1 score + latency + memory_peak**

- `target_token` 設為 `rate × avg_len`，使 FINCH 平均記憶體用量與我的方法等價
- 三個方法在**同一 task 的同一壓縮率**下比較，結果才有意義
- **target_token 一旦確定就不能改動**，否則不同實驗之間的比較失去意義

## 目前發現

### Llama 3.1 vs 2 的差異

原論文 Llama 2 在 512 target tokens + σ=93x（平均 47k context）還能跑出 19.1，比我們的更激進卻更好。最可能的原因：

Llama 3.1 的 attention pattern 比 Llama 2 更稀疏（rope scaling + 更長的訓練 context），question tokens 的 attention score 對 context 的影響分布更均勻，導致 FINCH 的 top-k 選擇品質下降，無法準確挑出跟問題最相關的 tokens。

### 數據鐵證：Score 與 chunk 數量高度負相關

以下是按 context 長度分 bin 的分析，證明**壓縮迭代次數越多，品質崩塌越嚴重**：

**narrativeqa（target=9137，split_size=512）**

| Context 長度 | 樣本數 | FINCH F1 | FullKV F1 | 保留率 |
|---|---|---|---|---|
| 5k-10k（< target，未壓縮） | 19 | 26.76 | 26.76 | **100.0%** |
| 10k-20k（20-40 chunks） | 56 | 21.24 | 23.93 | 88.7% |
| 20k-30k（40-60 chunks） | 10 | **0.00** | 10.83 | **0.0%** |
| 30k-50k（60-80+ chunks） | 88 | **8.01** | 29.12 | **27.5%** |

三個 task 都呈現一致的趨勢：**chunk 數量越多 → F1 越低**。

### 三層根因分析

#### 根因 1：GQA 導致 attention score 的 token selection 信噪比下降

| | Llama 2-7B | Llama 3.1-8B |
|---|---|---|
| KV heads | **32**（MHA） | **8**（GQA） |
| Query heads | 32 | 32 |

FINCH 的核心操作是 `layer_attention.sum(dim=1)` — 把所有 head 的 attention 加總。

- **Llama 2**：32 個獨立 KV head → 32 組獨立 attention pattern 投票 → 加總後信號集中
- **Llama 3.1**：8 個 KV head，每個被 4 個 query head 共享 → 有效獨立投票只有 8 組，信噪比降約 4×

#### 根因 2：RoPE theta=500000 讓 attention 分布更均勻（最根本的原因）

| | Llama 2 | Llama 3.1 |
|---|---|---|
| rope_theta | 10,000 | **500,000** |
| 訓練 context 長度 | 4k | **128k** |

- **Llama 2**：attention 有明顯的「局部峰值」→ top-k 容易選對
- **Llama 3.1**：attention 更**平坦** → top-k 第 100 名和第 500 名差距很小 → 容易選到無關 token

#### 根因 3：迭代壓縮的複合誤差

| Task | Chunks 數 | re-selection 輪數 | (0.98)^N |
|---|---|---|---|
| qasper | 10 | 9 | 0.83 |
| multifieldqa | 14 | 13 | 0.77 |
| **narrativeqa** | **59** | **58** | **0.31** |

完美解釋了為什麼 narrativeqa 掉最多（46.2% of fullKV）而 qasper/multifieldqa 相對好（74-75%）。

## 實驗過程與結論（已完成）

### 假說 1：split_size 太小導致過多迭代，加大可改善

**實驗**（全部 200 樣本，固定 target_token=9137）：

| 實驗 | split_size | F1 | 結論 |
|------|-----------|-----|------|
| Baseline | 512 | 12.62 | — |
| A | 2048 | 12.81 | 幾乎無改善 |
| B | 4096 | 9.15 | 反而更差（OOM風險，attention 品質更差） |

**結論：split_size 不是瓶頸。** 加大 chunk 雖減少迭代次數，但每個 chunk 的 attention 信號更難聚焦，抵銷了迭代減少的好處。

### 假說 2：固定 target_token 對長文件過度壓縮，per-sample adaptive 可改善

**實驗**（compression_rate=0.3063，per-sample adaptive target）：

| 實驗 | split_size | F1 | 結論 |
|------|-----------|-----|------|
| C | 512 | 8.25 | 比固定差 |
| D | 2048 | 9.71 | 仍比固定差 |
| E | 4096 | 5.22 | 最差（27 OOM） |

**結論：per-sample adaptive target 反而更差。** 可能原因：長文件原本能靠多保留 token 彌補 attention 不準，adaptive 強制削減反而傷害更大。

### 假說 3：GQA 導致 attention sum 信噪比低，per-head vote 可改善

**實驗設計**：把 32 Q heads reshape 成 8 KV groups，每個 group 獨立 top-k 後 vote，用 vote count 取代 uniform sum。

| 實驗 | 設定 | F1 | vs FINCH orig |
|------|------|-----|--------------|
| per_head_vote | vote_r=k（最寬鬆） | **13.70** | **+1.08** ✓ |
| vote_r=k/2 | vote_r=4568（嚴格） | 11.61 | -1.01（更差） |

**結論：per_head_vote=True, vote_r=k 是最佳設定。** vote_r 縮小反而更差，說明 Llama 3.1 attention 太分散，嚴格的 majority voting 會丟掉重要 token。

### 三 task 最終比較

| Task | FullKV | FINCH orig | FINCH+per_head | Gap 縮小 |
|------|--------|-----------|---------------|---------|
| narrativeqa | 26.53 | 12.62 | **13.70** | 1.08（7.8%） |
| qasper | 46.94 | 35.17 | 34.77（未跑） | — |
| multifieldqa_en | 48.15 | 35.72 | **39.87** | 4.15（33.4%） |

multifieldqa 改善顯著（chunk 少），narrativeqa 改善有限（58 輪迭代複合誤差為框架固有限制）。

### 最終結論

在不改動 FINCH 核心方法（chunk-wise, prompt-guided token dropping）的前提下：
- **per_head_vote=True** 是框架內最有效的改進
- narrativeqa 的大 gap 來自 58 輪迭代複合誤差 × Llama 3.1 attention 分布平坦，這是方法本身在長文件上的固有限制
- 繼續調整超參數（condition、vote_r 等）的邊際效益極低
