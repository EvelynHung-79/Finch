## Condition 選擇分析

| Condition	 | 適用場景	   | 原因                      |
|------------|------------|--------------------------|
| question	 |單文件 QA、paper QA |	答案藏在與 question 高度相關的段落，attention 偏向 question 能精準定位 |
| all	     |多跳 QA、synthetic（retrieval/count）、code |	需要保留多個不同段落的資訊；multi-hop 的橋接資訊跟 question 的 attention 可能很低；code completion 的相關 tokens 分散在整個 repo |
| context	 |摘要任務	   | 要保留整體文件結構，question 本身是 summary prompt，不能以它為主導 |

condition=question 有意義的前提： question token 要有足夠的 content-specific 語義，能指向 context 中的相關區域。
condition=context 有意義的前提： 任務答案需要全文理解，question 本身語義太弱或太通用。

condition=all 適合： 兩者都有一定貢獻，或保守地不想偏一邊。

## 為什麼 Llama 3.1 的表現比 Llama 2 差（目前說法）

目前最有證據支持的解釋不是模型能力退步，而是 FINCH 這類 attention top-k token dropping 方法在 Llama 3.1 上更容易失真。

1. **GQA 降低有效投票數，token selection 信噪比下降**
	- Llama 2（MHA）有 32 個獨立 KV heads。
	- Llama 3.1（GQA）只有 8 個 KV groups（32 個 Q heads 共享 8 個 KV heads）。
	- FINCH 以 head attention 加總做排序時，獨立投票來源變少，排序穩定性更差。

2. **長 context 設計使 attention 更平坦，top-k 區分度變差**
	- Llama 3.1 的 RoPE 設定（如較大 rope theta）與長上下文訓練（128k）使 attention 分布更均勻。
	- 在分數接近時，top-k 容易選到非關鍵 token。

3. **迭代壓縮造成複合誤差，長文件任務最明顯**
	- chunk-wise 重複 re-selection 會累積小錯誤。
	- context 越長、chunk 數越多，誤差放大越嚴重，F1 更容易崩塌（narrativeqa 最典型）。

4. **替代假說已被多組實驗弱化**
	- 單純放大 split_size 沒有穩定改善，甚至可能更差。
	- per-sample adaptive target 在目前設定下也沒有改善。
	- 這些結果支持「核心瓶頸在 attention ranking 品質與多輪誤差累積」。

5. **框架內可行改善：per-head vote**
	- 在不改動 FINCH 核心流程前提下，per-head vote 是目前最有效的改進。
	- 可部分回補分數（例如 multifieldqa 明顯改善），但對超長文件的上限仍受方法本身限制。

**一句話總結**：Llama 3.1 在 FINCH 下表現較差，主要來自「attention 更平坦 + GQA 投票信號較弱 + 長文件多輪壓縮誤差累積」三者疊加。
